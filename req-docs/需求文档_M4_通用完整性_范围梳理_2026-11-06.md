# 需求：M4 · 通用完整性（范围梳理）

一句话：炼妖壶在玩法已经能完整转起来之后，这一版专门把「进度别丢、改版别崩、测得住人」补牢，方便以后迁 Unity 或拉别人一起改也不踩坑。

> 版本：范围草案 | 日期：2026-11-06 | 状态：梳理稿（M3 封板后下一里程碑）  
> 需求目录：`req-docs/`  
> 读者：产品/玩家设计师（可跳过实现细节）；开发按后文功能条执行。

---

## 为什么要做这个大版本（给非开发）

M1–M3 做的是**游戏好不好玩、流程通不通**：炼化、野外、战斗、立绘、自动战斗……你能直接看见。

M4 做的大多是**你看不见、但进度和协作靠它**的东西，可以想成三件事：

1. **别把玩家进度弄丢或弄坏**  
   存档格式以后还会变。如果没有版本号和坏档提示，读到一份「半新半旧」的档可能直接白屏，玩家不知道是自己的问题还是游戏坏了。

2. **改代码时有人盯着底线**  
   现在有一些过期测试还在报假警报。M4 把验收理顺，以后加功能时能较快知道「是真坏了还是测试旧了」。

3. **为迁 Unity（M5）铺路，而不是在 Unity 里再救一次火**  
   Unity 会重做画面，但规则和存档要能带走。M4 把存档契约、设置边界写清楚，迁的时候少返工。

**一句话**：M4 不是新玩法版本，是「把已经能玩的游戏，做成以后改也不容易塌」的版本。

## 要做的功能（建议全部进 M4）

### F1. 存档版本号
- 行为：写入玩法槽时带 `version`（整数或 semver 字符串，实现时定一种）；读档时识别。  
- 边界：不做复杂迁移表（最多：旧档无 version 视为「M3 封板档」仍可读）；不做云同步。  
- 确认：新存一档 → 文件/解析结果里有 version；故意改坏 JSON → 有明确失败提示而非白屏。

### F2. 读档 / 坏档友好提示
- 行为：缺字段、JSON 损坏、版本过新（可选）时 toast 或弹层说明「档坏了 / 需要更新游戏」，不进入半残状态。  
- 边界：不自动修复玩家内容；不上传档到服务器。  
- 确认：用手改坏槽位 JSON → 读档看到人话错误，内存局不被污染。

### F3. 设置边界写清并扫尾
- 行为：文档与手册写明：设置（演出/自动）本机一份、不跟五槽走；玩法进度跟槽走。必要时设置页补一句说明。  
- 边界：仍不做音量/全屏/键位（除非本版末尾有余力）。  
- 确认：改设置 → 换槽读档 → 自动战斗偏好仍在；玩法素材随槽变化。

### F4. 验收债清理（A8 结转）
- 行为：修或删过期断言；点名套件对「M3 已声称功能」全绿或文档明示豁免。  
- 边界：不借机大改玩法。  
- 确认：`python acceptance/run_acceptance.py`（若仍用）与点名的 node 套件按清单通过。

### F5. 「冒险中」态更明显（可选但建议）
- 行为：顶栏或菜单旁短文案/样式表示正在野外格子上，存读禁用原因一眼能懂。  
- 边界：不改撤退/回档规则。  
- 确认：进图后能看出「冒险中」；出图后恢复。
